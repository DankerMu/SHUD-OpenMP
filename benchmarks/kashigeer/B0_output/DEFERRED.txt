# What's wrong

`SHUD/Basins/kashigeer/input/ksge/ksge.tsd.forc` declares 941 forcing
stations starting with `X76.45Y38.05.csv`, but `SHUD/Basins/kashigeer/
forcing/` only ships 403 CSV files and the very first station (the entire
`X76.*` column band) is missing. Running `./shud ksge` aborts immediately
with `Reading fail, file = .../forcing/X76.45Y38.05.csv` and exit code
12 (FILEIO) before CVODE is even constructed, so there is no B0 output
to archive on the local laptop endpoint.

This is a pre-existing case-data deployment gap that long predates
issue #11. It traces back to the NWM dataset slice that was used to
populate `Basins/kashigeer/forcing/` during S0-2 (#4) — the forcing
download was partial — and was not caught by S0-4 (#6) manifest checks
because manifest registry does not cross-check tsd.forc station count
against on-disk CSV count. The missing band (X76.*) covers Tarim
glacier headwater grid points that AutoSHUD identified as essential
for kashigeer but were never delivered.

# Why this is *not* in scope for #11

#11 (S0-8b) is the local-endpoint B0 archive driver. It SHALL skip
cases that cannot be executed because of upstream input data issues,
since fabricating a B0 baseline on partial forcing would silently
produce a misleading hash that future B1a/B1b comparisons would lock
themselves against.

# Pointer for resolution

S0-8c (#12) covers the server-side B0 archive workflow where the
authoritative NWM forcing tree lives at /volume/data/nwm/Basins on the
production node. Restoring the full 941-station kashigeer forcing set
SHOULD happen there as a follow-up to (or alongside) #12, then the
local-endpoint archive run for kashigeer can be re-attempted under
issue #11 (re-open or follow-up issue), or it can be reclassified as
server-only in benchmarks/INDEX.md.

Until then this DEFERRED.txt is the placeholder occupying
benchmarks/kashigeer/B0_output/. The other four NWM local-endpoint
cases (keliya, xinanjiang_upstream, qinyijiang, qhh) are archived
normally under #11.
