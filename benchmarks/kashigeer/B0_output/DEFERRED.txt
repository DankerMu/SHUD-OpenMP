# What's wrong (updated by S0-8c / #12 with server-side evidence)

`SHUD/Basins/kashigeer/input/ksge/ksge.tsd.forc` declares 941 forcing
stations starting with `X76.45Y38.05.csv`, but the corresponding
`forcing/` directory ships only 403 CSV files, and the missing band
covers the entire `X76.*` and `X77.*–X79.*` columns. Running
`./shud ksge` aborts immediately with
`Reading fail, file = .../forcing/X76.45Y38.05.csv` and exit code
12 (FILEIO) before CVODE is even constructed.

# Endpoint cross-check (S0-8c)

| Endpoint | tsd.forc declared stations | Actual forcing/ CSV count | X range present |
|---|---|---|---|
| Local Mac `SHUD/Basins/kashigeer/forcing/` | 941 (first X76.45Y38.05) | 403 | X80.25 → X84.05 |
| Server `/<server-data-root>/Basins/kashigeer/forcing/` | 941 (first X76.45Y38.05) | 403 | X80.25 → X84.05 |

The two endpoints carry the *same* incomplete forcing slice. This is
NOT a local-deployment regression from S0-2 (#4); it is an upstream
NWM dataset gap where the `kashigeer/forcing/` directory was populated
from a different X-band (X80–X84, looks like an adjacent basin slice
such as the Kuqa or Tarim mainstem) than the metadata
(`ksge.tsd.forc`) demands (X76–X80 Tarim glacier headwater).

# Why this is *not* in scope for #11 / #12

#11 (S0-8b) is the local-endpoint B0 archive driver and #12 (S0-8c) is
the server-endpoint counterpart. Both SHALL skip cases that cannot be
executed because of upstream input data issues, since fabricating a
B0 baseline on partial forcing would silently produce a misleading
hash that future B1a/B1b comparisons would lock themselves against.
