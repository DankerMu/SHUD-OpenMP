Phase 6 delta findings:

#### 🟡 Warning: Positive sentinel `The successful end.` is emitted pre-dtor, not post-dtor

`.github/workflows/serial-baseline.yml:1449-1457` + `SHUD/src/ModelData/Model_Data.cpp:32,40` + `SHUD/src/Model/shud.cpp:291,507`.

The Phase 6 gate replaces the broken `LEAK SUMMARY:` grep with a positive grep for `'The successful end.'` on stdout. The workflow comment claims this string "is emitted on the normal main() return path AFTER all init + state writes; if `_exit/abort/crash` bypasses normal return, marker absent → gate fails". This is partially correct, but the actual emission point is `Model_Data::TimeSpent()` (called from `modelSummary(1)` at `src/Model/shud.cpp:291` and `:507`), which fires BEFORE the SHUD solver function returns and BEFORE main returns and BEFORE `~Model_Data()` runs. So the sentinel proves:

- Solver reached its normal end-of-loop print (sufficient signal against any `_exit(0)` that fires mid-solver or any pre-`modelSummary` crash).
- NOT sufficient signal that the destructor chain ran to completion — a regression that inserts `_exit(0)` AFTER `modelSummary(1)` but BEFORE main return (e.g. between `N_VDestroy` and `return 0`) would still pass the gate while bypassing dtors.

This is a strictly tighter gap than the round-1 broken `LEAK SUMMARY:` gate (which inverted clean and dirty), and the comment block at L1449-1456 honestly describes the intent. But the gate's claimed converse direction ("positive emission proves full dtor coverage") is over-stated; the actual property is "positive emission proves the solver reached its summary print". Per the test-evidence rubric, this would be caught only by a marker emitted from within `~Model_Data()` itself (or equivalently from an `atexit`-registered marker that fires after the dtor chain).

Recommended fix (pick one, low priority):
- Add a `screeninfo("~Model_Data dtor complete.\n")` at the end of `Model_Data::~Model_Data()` after `FreeData()` returns, and grep for that string instead — this would make the gate actually post-dtor.
- OR weaken the workflow comment to say "positive emission proves the solver reached `modelSummary(1)` normally; combined with `halt_on_error=1` (sanitizer errors hard-fail) and the implicit reasoning that the dtor chain runs after `modelSummary(1)` without any conditional, the gate gives strong-but-not-tight dtor-coverage signal."
- OR document in PR body that the gate's positive emission is "necessary-but-not-sufficient for dtor coverage; canonical dtor-coverage evidence is the Mac shud_asan post-Phase-6 re-verify section + the deferred Phase 2 server valgrind heihe".
