- Severity: critical
  Failure class: inverted-predicate / wrapper-faithfulness (the gate observes a signal that means the OPPOSITE of what the gate asserts)
  Contract or invariant: design.md §D5 Invariant Matrix row "CI `asan-ubsan (keliya)` job 日志 grep `LEAK SUMMARY:` 命中 (确认 dtor 全程跑, 非 `_exit` 短路)" + REQ-3 dtor coverage gate wording in `.github/workflows/serial-baseline.yml:1444-1466`.
  Scenario or repro: The grep regex at workflow line 1449 is `'^==[0-9]+==(ERROR: LeakSanitizer:|SUMMARY: AddressSanitizer: detected memory leaks)|LEAK SUMMARY:'`. LeakSanitizer's documented behavior (https://github.com/google/sanitizers/wiki/AddressSanitizerLeakSanitizer): the `LEAK SUMMARY:` line is emitted **only when leaks are detected**; a fully clean run produces zero LSan output. Empirical test:
    - clean stderr (no LSan output) → `grep -c` returns `0` → the gate's `if [[ "$leak_summary_count" == "0" ]]; then exit 1` fires.
    - stderr with `LEAK SUMMARY:` (leaks present) → count ≥ 1 → gate passes.
  Therefore the gate's predicate is inverted: it requires that the run LEAKS (or that LSan otherwise emits LEAK SUMMARY) for the job to be "dtor-full CLEAN". The SHUD `./shud keliya` post-fix run, which the PR claims achieves clean dtor execution, would have NO LSan output and would hard-fail this gate. The gate cannot have been validated against a clean run because:
    a) it never executed on this PR (the `data_available` predicate at workflow line 1413 skipped the step — verified via `gh run view --job 83998346479 --log` showing `::notice CI runner has no keliya forcing/input data; … sanitizer run SKIPPED`);
    b) the Mac evidence file `valgrind_keliya_postfix.log` lines 36-42 documents that Mac ASan does NOT support `detect_leaks=1` at all (no Darwin LSan port), so the Mac smoke could not have exercised this codepath either.
    Secondary issue: even if the predicate were corrected, the gate STILL doesn't exercise `tools/p8tune.D/{dump_adjacency,fd_color_jacobian}` — those binaries are not invoked from any CI job (verified: `grep -n 'shud_asan\|dump_adjacency\|fd_color_jacobian' .github/workflows/serial-baseline.yml` shows only `shud_asan` lines). So even with the predicate fixed, future regressions in the spike binaries' exit path are NOT caught by this CI surface.
  Required test or evidence: Two coupled fixes:
    1. Invert the gate logic. The correct LSan-based dtor-coverage assertion is "if ASan ran AND we did NOT see `LeakSanitizer: detect_leaks is not supported on this platform.` AND we did NOT see `ERROR: LeakSanitizer: detected memory leaks` then dtor coverage is implicit (LSan ran its at-exit check and found nothing to report)". A simpler positive signal: grep for the **process-exit indicator** that LSan ran at all — e.g. require `==[0-9]+==WARNING|==[0-9]+==INFO|==[0-9]+==ERROR` absence as the success criterion, or require an LSan-specific exit-time string like `ASAN: __asan_handle_no_return` not appearing (no abort path taken).
    2. Reproduce one explicit positive control by introducing a deliberate heap-leak commit in a draft branch and confirming the corrected gate flags it; then revert. This proves the gate actually catches real regressions before claiming protection.
  Sibling surfaces: design.md §D5 last regression row; spec REQ-3 Scenario "_exit(0) workaround removal" relies on this gate for "future regression protection"; the PR commit message body line "future regression protection" depends on this gate semantically.
  Blocks merge: yes
  Impact: The gate is structurally false-positive AND structurally false-negative simultaneously: it would FAIL a clean dtor-full run and PASS a regression that introduces leaks but also keeps dtors running. Either outcome breaks the regression-protection contract. Compounded by the spike binaries not being CI-covered at all, the PR's stated "dtor-coverage CI protection" is illusory.
  Requested fix: Either correct the gate logic (preferred — change to negative assertion: "no `==PID==WARNING|ERROR` lines AND no `LeakSanitizer: detect_leaks is not supported` line; presence of LSan-clean exit code is sufficient evidence") OR remove the gate and replace with an explicit positive marker emitted by SHUD main itself (e.g. SHUD prints `[shud] dtor chain completed normally` at the end of `~Model_Data()` and CI greps for that token). The latter is more direct — it tests the actual SHUD contract rather than an LSan side-effect.
