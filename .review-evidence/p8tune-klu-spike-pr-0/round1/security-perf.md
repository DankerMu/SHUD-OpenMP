- Severity: major
  Failure class: Pre-flight RSS estimator under-counts by ~4× empirically, scales poorly with fill ratio
  Contract or invariant: REQ-5 RSS axis Scenario "RSS axis threshold" — `peak_RSS < 0.7 × CN_NODE_RAM_BYTES`; Scenario "OOM-as-data-point" — preflight or post-factor RAM check SHALL classify OOM cells correctly.
  Scenario or repro: keliya Mac smoke shows preflight `est_bytes=770560` (0.7 MB) vs actual `peak_rss=3145728` (3 MB) — preflight UNDER-counts by 4.1× (see `.review-evidence/p8tune-klu-spike-pr-0/mac_smoke_keliya_klu_factor.log` L3 and L12). The estimator at klu_analyze_factor.cpp:232 is `est = total_nnz·64 + NumY·64`, which counts only the input A matrix footprint with a ~4× pad — it does NOT account for KLU's fill (Numeric->lnz + unz, which for keliya AMD+BTF is 33088 entries vs A's 10255, i.e. 3.2× fill; for natural ordering on heihe_x16, fill could be 50-100×). At heihe_x16 NumY≈760K, total_nnz≈6·NumY≈4.5M → preflight est ≈290 MB while a 100× fill numeric factor would need ≈14 GB JUST for L+U doubles, plus AMD/COLAMD permutation working set. Preflight will say "PASS, proceed" and klu_factor will OOM-trigger Linux OOM-killer before the post-factor check at L282 even runs. The post-factor check only catches OOM if SuiteSparse cleanly returns `KLU_OUT_OF_MEMORY`; an OOM-killed process never reaches L282.
  Required test or evidence: Compare the preflight estimator output against actual `numeric_lnz+unz` for all 4 cases × 4 orderings (16 cells) in the Mac smoke (keliya only is insufficient signal). Add a calibration multiplier: `est = (A_nnz · expected_fill · 24B + n · 64B) · 1.5_safety`. Use Symbolic->lnz+unz (already computed by klu_analyze before klu_factor at L250) as the expected-fill anchor — that requires moving the preflight CHECK to between klu_analyze and klu_factor (currently it's before klu_analyze at L228-239). REQ-5 Scenario "OOM-as-data-point" explicitly requires the tool to exit 0 + emit `KLU_OOM_DETECTED`; an OOM-killed process exits 137 + emits nothing → Slurm sees a task failure and the OOM data point is lost.
  Sibling surfaces: At heihe_x16 χ=expected-large (per master plan §P8-tune.D), fd_color_jacobian's per-color FD probe also runs on the same cn-node; if KLU OOM-killer fires, both stages' artifacts are lost. The aggregator in PR-B must classify OOM-killed cells; currently the spec only enumerates `KLU_OOM_DETECTED` + non-zero-return paths, not signal-9 paths.
  Blocks merge: no (PR-0 is keliya-only Mac smoke; the estimator gap manifests at PR-A on heihe_x4/heihe_x16). But the estimator must be calibrated BEFORE PR-A or PR-A artifacts may be incomplete.
  Impact: heihe_x4 / heihe_x16 cells may silently OOM-kill instead of cleanly emitting `KLU_OOM_DETECTED`, violating REQ-5 OOM-as-data-point and forcing manual sacct triage at PR-A.
  Requested fix: (a) Move RSS preflight check to AFTER `klu_analyze` so `Symbolic->lnz + Symbolic->unz` is known; recompute `est = (Symbolic->lnz + unz) · 24 · 1.5` and gate against `CN_NODE_RAM_BYTES`. (b) Document in `README.md` §pre-flight-limitations that signal-9 OOM-kill is possible at heihe_x16 + natural ordering and PR-A's spike_array.sbatch should set `--mem` accordingly + use `sacct` post-mortem to detect signal-9 cells.

Non-blocking notes:
- `std::fread` return values are not checked in `read_csc` (fd_color_jacobian.cpp:94-99) and `read_jbin` (klu_analyze_factor.cpp:83-91). With internal trust boundary (file producer = pipeline's prior stage) this is acceptable; if PR-A ever consumes binaries from a different source, add explicit return-value checks to guard against truncation/UB on uninitialized fields.
- `dump_adjacency.cpp:399` declares `extern int optind;` manually instead of including `<unistd.h>` for the POSIX declaration. Works on glibc + libc++ but is brittle; prefer `#include <unistd.h>`.
- The `peak_rss_bytes()` cross-platform unit handling at klu_analyze_factor.cpp:96-113 is CORRECT: Mac uses mach (bytes), Linux uses `ru_maxrss · 1024` (KB→bytes). The comment at L108 matches the implementation.
- `omp_set_num_threads(1)` at fd_color_jacobian.cpp:196 is correctly justified for determinism, and the keliya FD probe at NumY=1785 with χ=16 is fast enough (~30s Mac smoke per `mac_smoke_keliya_fd_color.log`). No perf concern at heihe_x16 because ColPack coloring is O(NumY·χ) ≈ 580M ops, dwarfed by the χ rhs_core calls (each O(NumY)).
- The Mac smoke wall numbers (`numeric_factor_wall_sec=0.000444`) are too small to be reliable on shared CPU and not used in any gate — informational only, correctly so. The determinism gate is sha256 of the J binary, not wall.
- No secrets, credentials, API tokens, or SSH key material found in the 26 changed files. `cn_ram_probe.log` exposes only `MemTotal`/cn14 hostname which are part of the public sweep's audit trail.
