### 3.6 AC6 — cv_y_hash line count consistency

For mode A and mode B alike: every cell produces a `cv_y_hash.txt` with
either **6480** lines (keliya) or **12960** lines (qhh), with one
exception:

- `A_qhh_N2_rep2`: 3021 lines instead of 12960.

Investigation (honest account; PR-C Phase 4.5 verifier corrected an
earlier draft that invoked two mechanisms — "CVODE internal-step dump
timing" and "Mac BSD `creat()` integer-second filename coalescing" — both
of which contradict the code surface):

- Cell `exit_code` = 0; `wall_sec` = 105 (normal); `cvode_stats.txt` =
  `nst=13000`, `nfe=13270` (matches every other A_qhh cell exactly).
- `qhh.rivqdown.sha256` = `ccc7dd09d0189ecd360cdc4bca9090acece08f51d7de8108ece6f32900a626e7`
  (bitwise-identical to every other A_qhh cell). **AC1 still PASSes for
  this group.**
- Code surface (`SHUD/src/Model/shud.cpp:177-194` the `while (t < tnext)`
  CVode loop; L202-223 the `SHUD_DUMP_CV_Y` block): the dump fires
  **after** the inner loop exits, so `t == tnext` — the dump is on the
  **output grid**, NOT the internal solver step. Filename format
  `%020.6f.bin` carries microsecond precision, so integer-second filename
  collision is structurally impossible.
- Observed timestamp pattern in this cell's `cv_y_hash.txt`: 3021 lines,
  first `tout = 12196540` (≈ 94% of the way through the run; the first
  ~99090 s of model time has no dump entry); inter-line gaps are 3008 ×
  10 s plus a sparse tail of 6 × 20 s and a handful of 30/40/50/70/80 s
  gaps. The dominant 10 s gap matches the regular output cadence of the
  other A_qhh cells; the anomaly is the missing **prefix**, not the
  spacing.
- A_qhh_N2_rep1 and A_qhh_N2_rep3 (same binary, same env, same
  `OMP_NUM_THREADS=2`) both produced full 12960-line `cv_y_hash.txt`
  files. The divergence is reproduction-rate 1/3 for this exact cell and
  did not recur in 47/48 other cells.

**Root cause: undetermined.** The pattern (most entries present at
correct cadence, large prefix missing, no other artifact damaged) is
consistent with an IO transient — e.g. a partial `fwrite`, a transient
`fopen` failure causing the early-tout `cv_y_<tout>.bin` files to be
absent so the downstream hasher emitted nothing for them, or filesystem
pressure during the prefix window. The current dump path returns void
from `fwrite`/`fopen` failures with only a `fprintf(stderr, ...)`
warning, which would not surface in `exit_code` and may have been lost
to the runner's stderr capture.

**AC6 result: WARN, not FAIL.** The hash file is an auxiliary debug
artifact; the SHALL gates (AC1, AC2) and the operational invariant
(rivqdown SHA + CVODE stats) all PASS for this cell. Tracked for PR-G
as an IO-robustness hardening item — check `fopen` return, verify
`fwrite` short-write path, consider `fsync` on critical hashes, or
aggregate per-tout dumps into a single appended file to remove the
N-files-per-cell open/write/close pressure. (The earlier "switch to
output grid" suggestion is moot: the dump is already on the output
grid.)

## 4. Findings and observations

### F1 — NVEC overhead is highly case-scale-dependent

At keliya (484 cells, 6480 model steps) mode B is **5.4× – 6.6× slower** than
mode A across all N. At qhh (4773 cells, 12960 steps, +lake module) the gap
collapses to **1.06× – 1.18×**. This is the expected NVECTOR_OPENMP signal:
fixed per-step parallel-region overhead (team spawn + reduction) dominates
the per-element vector cost at small N; only when the per-element cost is
already saturated by problem size does the parallel reduction start to
amortize.

**Implication for PR-E:** mode B is not a useful end-user mode at keliya
scale and is approximately neutral at qhh scale. The case for OpenMP
acceleration of SHUD must come from RHS parallelism (mode D), not from
NVECTOR alone. This validates the master-plan §6 design D1 prediction that
PR-N/strict-mode work targeting the RHS is the path to actual speed-up.

### F2 — Mode B does NOT scale with OMP_NUM_THREADS

For keliya `B` the N=1 mean is 203.7 s, the N=8 mean is 190.3 s — speedup
**1.07×** at 8 threads. For qhh `B` the matrix is essentially flat at ~115 s.
That is, NVECTOR_OPENMP gets the *overhead* of being parallel without the
*scaling benefit*, because the dominant cost stays in serial RHS.

This is also expected and is exactly why the OpenMP master plan introduces
the strict OMP RHS modes (C/D) — modes B is by design "instrumentation only"
on the way to D.

### F3 — Mode A is truly thread-invariant (AC2 PASS)

A solid empirical PASS on AC2 is the load-bearing result: it confirms that
the existing OMP build of SHUD does not accidentally invoke a reduction
in mode A's serial RHS pathway. Mode A is therefore a clean reference
the upcoming PR-E SHALL gate can compare against without false positives.

### F4 — CVode stats are deterministic per (build, case)

12/12 cells in each (build, case) bucket emit the same nst/nfe/nni/netf
values. Solver determinism at fixed (build, case) is a property the OpenMP
master plan relies on for cross-N comparison; this is the first formal
confirmation we have at qhh scale on Mac.

### F5 — Failed cells recovered via runner hot-fix

The main batch failed 4 cells with rc=126 after the SHUD model itself
reported rc=0:
- `A_qhh_N1_rep1` (wall 179s, FAIL rc=126)
- `A_qhh_N1_rep2` (wall 213s, FAIL rc=126)
- `A_qhh_N1_rep3` (wall 199s, FAIL rc=126)
- `A_qhh_N2_rep1` (wall 194s, FAIL rc=126)

Root cause: `tools/p1e_2x2_runner.sh` line 407 used
`rm -f "$OUTPUT_DIR_ABS"/cv_y_*.bin` after the run. For qhh the dump produces
~12960 cv_y_<tout>.bin files; with `$OUTPUT_DIR_ABS` ≈ 85-byte absolute path,
the post-glob `rm` arg list reached ~1.1 MB — over Mac BSD's default
ARG_MAX (256 KB). The shell aborted the cleanup with
"Argument list too long" and `rm` exit 1, which bash propagated as the
runner's overall exit 126 even though the SHUD run had already succeeded
and the artifact directory contained valid `cvode_stats.txt`, `rivqdown.dat`,
and `cv_y_*.bin` files.

Hot-fix (committed in this PR as commit 1): replace the `rm -f` glob with
`find "$OUTPUT_DIR_ABS" -maxdepth 1 -name 'cv_y_*.bin' -delete`. `find`
has no argument-list ceiling because each pathname is processed in-place,
not as part of an exec argv. Linux has a much higher ARG_MAX (~2 MB) so
heihe is unlikely to hit the same limit immediately on the server, but
heihe_x4 (4× the cells of heihe at ~25k) would eventually exceed it.
`find -delete` eliminates the ceiling entirely.

The 4 affected cells were rerun cleanly after the hot-fix (see
`/tmp/p1e_pr_c_mac_rerun.log`); the rerun artifacts are bit-equivalent
to peers per AC1 PASS.

## 5. Decision implications for PR-E

PR-E (Phase 1 verdict) is the next milestone after PR-C and PR-D. Mac
evidence alone is insufficient for the verdict; PR-D must produce the
companion server-side evidence on heihe (6335 cells) + heihe_x4 (~25k
cells, NVECTOR_OPENMP's actual target scale).

Preliminary signal from PR-C:
- AC1 + AC2 PASS implies the SHALL reference (mode A) is suitable.
- AC5 wall-time pattern is "small case = pure overhead, medium case = neutral".
  Extrapolating to heihe scale on server: NVECTOR_OPENMP is unlikely to be
  net-positive even at heihe_x4 unless server libomp scheduling pulls
  ahead of Mac's libomp. This is the explicit question PR-D answers.
- AC4 mode A ≠ mode B is expected; it does NOT block PR-E.

If PR-D corroborates: PR-E happy path is **D12.1 (route to mode C/D via
PR-G)**. If PR-D shows surprising mode B scaling on heihe_x4, PR-E may
recommend keeping mode B as a packaged option, but the decision rests
on PR-D data, not PR-C alone.

```bash
#
# Build the two binaries (one-time per SHUD pin):
cd SHUD && make clean && make shud && make clean && make shud_omp && cd ..

# 48-cell batch (~2.5 h on M4 Pro):
mkdir -p /tmp/p1e_pr_c_mac_runs
for b in A B; do
  for c in keliya qhh; do
    for n in 1 2 4 8; do
      for r in 1 2 3; do
        tools/p1e_2x2_runner.sh \
          --case "$c" --build "$b" --N "$n" --rep "$r" \
          --out-dir "/tmp/p1e_pr_c_mac_runs/${b}_${c}_N${n}_rep${r}"
      done
    done
  done
done

# Aggregate and re-check gates:
tools/p1e_aggregate_mac.sh all   # prints markdown tables
tools/p1e_aggregate_mac.sh ac1   # exit 0 = PASS, nonzero = FAIL
tools/p1e_aggregate_mac.sh ac2
```

The aggregator is **idempotent**: it derives everything from the
per-cell artifact files, so it can be re-run for spot-checks without
re-executing SHUD.

Expected wall budgets per build on M4 Pro:
- A: ~1.0 s/cell × 12 cells (keliya) ≈ 6 min, ~100 s/cell × 12 (qhh) ≈ 20 min
- B: ~190 s/cell × 12 (keliya) ≈ 40 min, ~115 s/cell × 12 (qhh) ≈ 25 min
- Total: ~1.5 h serial, plus rebuild overhead.
