## 4. Findings and observations

### F1 — NVEC overhead size-dependence: the cliff is between 484-4773 cells

Combined with PR-C (Mac, keliya 484 + qhh 4773), this PR gives us a
4-point map of the NVECTOR_OPENMP overhead at fixed N=1:

| case scale | cells | platform | B/A ratio (N=1) |
|------------|------:|----------|----------------:|
| keliya     | 484   | Mac M4 Pro | **6.64x** |
| qhh        | 4773  | Mac M4 Pro | 1.18x |
| heihe      | 6335  | Xeon 5318Y | 1.02x |
| heihe_x4   | ~25k  | Xeon 5318Y | 1.03x |

The NVECTOR_OPENMP per-step parallel-region overhead (team spawn + barrier
+ reduction merge) is a fixed cost per RHS call; it dominates when the
per-element vector work is small (keliya at 484 cells), is approximately
neutral around 5k cells (qhh, heihe), and is absorbed entirely at 25k+
cells. The cliff is between 484 and 4773 cells on Mac; the server (with
gcc/libgomp) shows the cliff is even sharper — heihe at 6335 cells is
already at the asymptote.

**Implication for PR-E:** mode B is dead at keliya scale, neutral at qhh
through heihe scale, and finally net-positive at heihe_x4 scale. The
NVECTOR-alone path has a usable operating envelope only for very large
basins.

### F2 — Mode B intra-N scaling: 15 % speedup on heihe_x4, saturates at N=2

The headline data point. On `heihe_x4` (~25k cells):

- N=1: 1390.3 s
- N=2: 1207.7 s (1.151× speedup, -13.1 %)
- N=4: 1208.7 s (1.150× speedup vs N=1, no further improvement)
- N=8: 1209.3 s (1.150× speedup vs N=1, no further improvement)

The N=2 win plateaus immediately: N=4 and N=8 produce identical wall
times within run-to-run noise. This is consistent with the
"NVECTOR_OPENMP wraps a small fraction of total wall time, parallel
reduction dominates that fraction, second thread amortizes overhead, more
threads add nothing because the serial RHS bottleneck has come back into
view" reading. The serial RHS is still ~85 % of the total wall on
heihe_x4; NVECTOR_OPENMP can at best chip 15 % off the remainder.

On `heihe` (6335 cells) the same intra-N pattern shows up but weaker
(B N=1 535.3 s → N=2 506.7 s = 1.056× speedup), and again saturates at
N=2 with no benefit at N=4/N=8.

**Implication for PR-E:** mode B at heihe_x4 scale is a **real but
limited** win. The 15 % bound is too thin to justify mode B as the
end-user default — but it's enough to confirm that the NVECTOR
parallelism is *working as designed*. The path to real speedup (≥2×)
still requires RHS parallelism (modes C/D from PR-G).

### F3 — Mode A is truly thread-invariant on server libgomp (AC2 PASS)

The PR-C AC2 PASS on Mac (Apple libomp) generalizes to server libgomp.
No hidden parallel section, no surprise reduction; mode A is a robust
SHALL reference across both OMP runtimes the project will ship against
(macOS dev + Linux production).

### F4 — Heihe vs heihe_x4 cvode_stats sign-flip

Heihe: A nst 6698 vs B nst 6713 (+15 steps, +0.22 %).
Heihe_x4: A nst 6575 vs B nst 6572 (-3 steps, -0.05 %).

The direction of the cvode stats drift between modes A and B is not
monotonic in problem size — it can flip sign as the per-step
floating-point reduction error accumulates differently against the
adaptive step controller. This is a non-issue (both are well within the
1-2 % envelope, and AC1 confirms within-mode A bitwise identity is
preserved) but worth recording: it means we cannot use the cvode stats
delta as a proxy for floating-point error magnitude across problem
scales.

### F5 — Server batch is materially cleaner than Mac batch (AC6 perfect)

PR-C reported one A_qhh_N2_rep2 cell with truncated cv_y_hash.txt (3021
of 12960 lines) attributed to a likely IO transient on Mac. The server
48-cell batch produced zero such anomalies — all 48 cells have the
expected 6480-line cv_y_hash.txt. The combination of (a) the PR-C
ARG_MAX hot-fix landing before the server batch, (b) Linux ext4's higher
IO determinism vs macOS's APFS under heavy small-file pressure, and (c)
each Slurm job getting an isolated compute node, all plausibly
contribute. No code change is recommended on top of PR-C; the IO-hardening
item is still tracked for PR-G but the priority drops.

## 5. Decision implications for PR-E

PR-E is the Phase 1 verdict milestone. The combined PR-C (Mac, small +
medium) + PR-D (server, large + X-large) evidence is now complete:

### SHALL gate STATUS

- **AC1 (mode A 3-rep bitwise per (case, N))**: **PASS** on all 4 cases
  × 4 N × 3 reps = 96 cells (48 Mac + 48 server) when counted by SHALL
  scope (mode A only: keliya, qhh, heihe, heihe_x4 each at N=1/2/4/8 × 3
  reps = 48 mode A cells). Every (case, N) group is bitwise-identical
  across all 3 reps.
- **AC2 (mode A cross-N stability per case)**: **PASS** on all 4 cases.
  Mode A SHA is invariant under OMP_NUM_THREADS.

**Phase 1 SHALL criteria met. PR-E recommendation: VERDICT = Phase 1
PASS.**

### Mode B operating envelope

- **keliya (484)**: 5-7× slower than A; **dead**, do not ship.
- **qhh (4773)**: 1.1-1.2× slower than A; not useful, marginal.
- **heihe (6335)**: ≈ neutral vs A; weak intra-N scaling (1.06×).
- **heihe_x4 (~25k)**: 0.9× of A (B is faster); 1.15× intra-N speedup
  (saturates at N=2). The only scale where mode B is a net win.

### Implications for PR-F/G/I

The 1.15× ceiling on mode B at heihe_x4 N=2 is informative:

- **PR-F (env vars + dispatch wiring)**: should preserve mode B as an
  opt-in for heihe_x4-scale users via env-var gate (e.g.
  `SHUD_NVEC_BACKEND=omp`). Default should remain mode A until mode D
  data lands. No change to public API beyond an env var; the SHALL gate
  unblocks this.
- **PR-G (StrictOMP RHS, modes C/D)**: must deliver more than 1.15× to
  justify shipping. The master plan §6 D1 target was ≥2× on heihe_x4 at
  N=4; the mode B data confirms that NVECTOR alone cannot reach that
  ceiling, so the RHS parallelism work is essential. PR-G is **not
  optional** for the Phase 2 verdict.
- **PR-I (Phase 2 verdict)**: should compare mode D vs the mode A SHALL
  reference using the same 4-case × 4-N × 3-rep matrix; the 96-cell
  Phase 1 baseline is now established.

PR-E should also document the **N=2 saturation point** as a forecasted
boundary for any future StrictOMP work — if mode D shows the same N=2
plateau, the next bottleneck is amdahl-limited by the SUNDIALS linear
solve (SPGMR), and the path forward is preconditioner / matrix-free RHS
fusion (master plan §6 D2-D3). If mode D scales past N=2, the basin is
the RHS, not the solver.

# On the server, from /scratch/frd_muziyao/SHUD-OpenMP:

mkdir -p /tmp/p1e_pr_d_server_runs

## 7. Rerun history

The main batch (job IDs 9126-9173) submitted 48 sbatch jobs chained via
`-d singleton`. Two failed mid-batch:

Job-ID-to-cell mapping pattern: the 9126-9173 range maps in
chained-singleton submission order — for each stream (heihe first, then
heihe_x4), cells iterate A→B × N∈{1,2,4,8} × rep∈{1,2,3} alphabetically.
So job 9126 = `Aheihe_N1_rep1`, 9127 = `Aheihe_N1_rep2`, …,
9149 = `Bheihe_N8_rep3`, 9150 = `Aheihe_x4_N1_rep1`, …,
9173 = `Bheihe_x4_N8_rep3`. Reruns 9197/9198 sit outside the range.

| Job ID | Cell                 | Outcome    | Notes |
|-------:|----------------------|------------|-------|
| 9127   | Aheihe_N1_rep2       | FAILED 2:0 | wall ~509s |
| 9150   | Aheihe_x4_N1_rep1    | FAILED 2:0 | wall ~1352s |

Root cause (documented in-session): both failures occurred during a
mid-batch `rsync` from the orchestrator pulling partial artifact files for
preview. The rsync triggered NFS stale file handle errors on the live
output directory while the SHUD process was still writing the final
`rivqdown.sha256` and `cell.meta`. Slurm captured exit_code=2 from the
runner's post-write phase even though SHUD itself had completed
normally (cvode_stats.txt and the binary outputs were intact).

The fix was operational, not code:
- Job 9197 (rerun of Aheihe_N1_rep2): completed clean at 2026-06-25T16:15:43.
- Job 9198 (rerun of Aheihe_x4_N1_rep1): completed clean at 2026-06-25T21:53:15.

Both reruns overwrote the original (failed) cell directories. The
`/tmp/p1e_pr_d_server_runs/<cell>/cell.meta` files mirrored in this PR
correspond to the *rerun* artifacts (exit_code=0) for these two cells.
AC1 PASS implies the rerun outputs are bitwise-identical to the other
two reps in each group, which is the definitive cross-check that the
rerun recovered cleanly.

Operational lesson for PR-G / future server batches: never rsync from a
live `.p1e-runs/<cell>/` directory while the job is still running.
Mid-batch previews should pull only from cells already in Slurm
`COMPLETED` state.
